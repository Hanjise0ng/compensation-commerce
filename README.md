# compensation-commerce

쇼핑몰의 주문·결제를 구현하며, **결제 도중 실패가 생겨도 재고·쿠폰·포인트·결제 금액이
서로 어긋나지 않게** 하는 방법을 단계별로 만들어 가는 프로젝트입니다.

## 어떤 문제를 푸는가

주문과 결제 사이에는 외부 결제 대행사(PG) 호출이 끼어 있습니다.
PG 호출은 DB 트랜잭션으로 되돌릴 수 없어서 이런 일이 생깁니다.

- 결제는 거절됐는데 재고와 쿠폰이 묶인 채 남는다
- 돈은 빠져나갔는데 주문은 실패로 남는다
- 결제 결과를 알 수 없는데 재고를 풀어 버린다
  이 프로젝트는 단순한 구현에서 시작해 문제를 테스트로 재현하고, 보상 트랜잭션으로 고쳐 나갑니다.

## 기술

Java 21 · Spring Boot 4.1 · Spring Data JPA · MySQL 8.4 · Testcontainers · GitHub Actions

## API

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/api/orders` | 주문 생성. `Idempotency-Key` 헤더 필수 |
| GET | `/api/orders/{orderNo}` | 주문 조회 |
| POST | `/api/payments/confirm` | 결제 승인. 승인이면 200 `PAID`, 거절이면 200 `FAILED`, 결과를 알 수 없으면 202 `PENDING` |

## 설계 결정

| 주제 | 선택 | 선택하지 않은 방식과 이유 |
| --- | --- | --- |
| 재고 모델 | 창고 수량과 예약 수량을 분리 | 수량 하나: 결제 대기 중인 물량을 표현할 수 없다 |
| 재고 동시성 | 비관적 락, 상품 ID 순서로 잠금 | 낙관적 락: 한 상품에 주문이 몰리면 재고가 남아도 89%가 충돌로 실패했다. 락 없음: 오류 없이 재고의 4배가 팔렸다 |
| 중복 주문 방지 | 사전 조회 + DB UNIQUE 제약 | 사전 조회만: 동시 요청에서 둘 다 통과한다 |
| 결제하지 않은 주문 | 결제 기한을 저장하고 스케줄러로 만료 | 재고를 결제 시점에 차감: 결제 중에 품절될 수 있다 |
| 업무 규칙의 위치 | 도메인 객체의 메서드 | 서비스의 if문: 규칙이 여러 곳에 흩어진다 |
| 인증 | 포트 뒤에 숨기고 헤더 방식으로 임시 구현 | 처음부터 JWT: 주제에서 벗어난다. 나중에 구현만 교체한다 |
| PG 호출의 위치 | 트랜잭션 밖. 시도 기록 → PG 호출 → 확정의 세 구간으로 분리 | 트랜잭션 안: 처리량이 풀 크기 ÷ PG 응답 시간으로 고정됐다(초당 9.5건). 커넥션 풀 증설: 5배로 늘려도 분리한 구조의 53%였다 |
| PG 결과의 표현 | sealed 타입(승인, 거절, 불명)과 switch | 예외: 새 경우가 생겨도 처리를 빠뜨린 곳을 컴파일러가 알려 주지 않는다 |
| 결과를 알 수 없을 때 | 보류. 아무것도 되돌리지 않는다 | 즉시 보상: PG에서는 승인됐을 수 있어, 돈은 받고 재고는 풀어 버리게 된다 |
| 보상의 중복 실행 | 주문 상태를 먼저 바꾸고 낙관적 락으로 한쪽만 커밋 | 비관적 락: 드물게 겹치는 상황을 위해 매번 락 대기를 감수해야 한다 |
| 결제 진행 상황의 기록 | 결제 시도와 같은 트랜잭션에서 사가 기록(order_saga)을 저장 | 메모리에서만 추적: 서버가 멈추면 사라진다. 주문 상태에 추가: 상태 전이를 전부 다시 봐야 한다 |
| 끝나지 않은 결제의 처리 | 별도 워커가 PG에 조회해 확정 또는 보상 | 만료 스케줄러에 맡김: 기한만 보고 풀면 PG에서 승인된 결제의 재고를 놓는다 |
| 복구를 시작하는 시점 | 결제 시도 후 1분 뒤부터 | 즉시: 아직 응답을 기다리는 요청과 겹치고, PG가 처리 중인 거래를 "없음"으로 볼 수 있다. 15초로 단축: 서버가 금방 돌아오는 경우에만 약 42초 빨라지고, 서버가 오래 죽어 있으면 차이가 없었다 |
| 승인 후 확정 실패의 처리 | PG 결제 취소로 되돌림 | 그대로 둠: 돈만 나가고 주문이 없다. 계속 재시도: 규칙 위반은 몇 번을 해도 같다 |
| 되돌릴지 다시 할지의 기준 | 실패의 종류(업무 규칙 위반은 취소, 그 밖은 재확정) | 횟수 기준: 긴 장애 때 정상 결제가 취소된다 |
| 취소 재시도 간격 | 10초부터 두 배씩, 최대 10분 | 고정 간격: 처음엔 느리고 장애 중엔 PG에 부담이다 |
| 취소가 끝내 안 될 때 | 주문과 자원을 유지한 채 수동 처리 상태로 표시 | 주문을 실패로 닫음: 돈이 PG에 남은 채 기록만 끝난다 |

## 알고 있는 한계

- 주문 서비스가 재고·쿠폰·포인트 리포지토리를 직접 다룬다. 리팩터링 단계에서 도메인별 서비스로 나눈다.
- 주문번호가 겹치면 그 요청은 500으로 실패한다. 재요청하면 성공한다.
- 인증은 `X-Member-Id` 헤더를 그대로 믿는 개발용 방식이다.
- 재고의 비관적 락은 인기 상품 하나에 주문이 몰리면 사용자 수만큼 대기가 길어진다(동시 100명에서 p95 약 1초). 이 대기가 문제가 되는 규모에서는 조건부 UPDATE 같은 다른 방식을 검토해야 한다.
- 복구가 "PG에 거래 없음"으로 판단해 보상한 뒤에 PG에서 승인이 확정되는 경우는 막지 못한다. 복구 시작 시점을 PG의 승인 유효 시간보다 길게 잡아 줄일 뿐이다.
- 수동 처리 대상(`COMPENSATION_FAILED`)을 알리는 수단과 관리 화면이 없다. 지금은 SQL로 조회한다.
- PG 조회가 계속 답이 없는 결제는 최대 10분 간격으로 끝없이 다시 확인한다. 한도와 알림이 없다.
- 실행용 PG가 가짜 구현이라 "이미 취소된 결제를 다시 취소"하는 경우의 실제 응답은 확인하지 못했다. 실제 PG를 연결할 때 어댑터에서 다룬다.

## 실행

Docker가 필요합니다.

```bash
# 테스트 (MySQL은 Testcontainers가 띄웁니다)
./gradlew test
 
# 서버 실행
docker compose up -d
./gradlew bootRun
```

```bash
curl -X POST http://localhost:8080/api/orders \
  -H "X-Member-Id: 1" \
  -H "Idempotency-Key: demo-001" \
  -H "Content-Type: application/json" \
  -d '{"items":[{"productId":1,"quantity":1}]}'
```

회원, 상품, 재고 데이터는 직접 넣어야 합니다.
